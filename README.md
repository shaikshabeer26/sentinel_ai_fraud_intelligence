# SENTINEL — AI Fraud Intelligence
> An AI-powered transaction fraud risk intelligence system that combines machine learning, behavioral analysis, relationship intelligence, anomaly signals, and explainable decisioning.
SENTINEL is designed to analyze a transaction in real time and produce an interpretable fraud-risk assessment rather than relying on a single machine-learning probability.
---
## 🚀 Overview
Fraud detection systems often face a difficult problem:
- Fraud patterns continuously change.
- A single ML probability may not provide enough context.
- Legitimate transactions can be incorrectly blocked.
- Fraud decisions need to be explainable.
- Risk teams need actionable signals rather than only a prediction.
SENTINEL addresses this by combining multiple intelligence layers into a unified risk decision pipeline.
### SENTINEL Pipeline
```text
Transaction
     ↓
Feature Processing
     ↓
AI Fraud Model
     ↓
Behavioral Intelligence
     ↓
Relationship Intelligence
     ↓
Anomaly Signals
     ↓
Risk Score Fusion
     ↓
Explainable Decision
     ↓
APPROVE / REVIEW / BLOCK

🧠 Core Intelligence Layers
1. AI Fraud Model
  SENTINEL uses a Random Forest fraud classifier with balanced class weighting.
  The model produces a fraud probability for each transaction.
  Example:
  AI Fraud Probability: 2.00%
  Operating Threshold: 45%
  The model probability is one component of the final decision rather than the only signal.
2. FraudDNA — Behavioral Intelligence
  FraudDNA analyzes transaction characteristics and behavioral patterns such as:
  Transaction amount
  Transaction timing
  Transaction distance
  Payment characteristics
  Identity and email information
  These signals provide additional behavioral context around the AI prediction.
3. FraudChain — Relationship Intelligence
  FraudChain provides relationship-based intelligence.
  It considers historical associations between transaction entities and identifies potentially connected patterns.
  Examples include:
  Repeated entity relationships
  Historical fraud associations
  Connected transaction attributes
  Recurring suspicious relationships
  This allows SENTINEL to consider historical context instead of treating every transaction as an isolated event.
4. Anomaly Intelligence
  SENTINEL also considers unusual transaction characteristics that may provide supporting evidence.
  Examples include:
  Unusual transaction timing
  Elevated transaction amount
  Unusual geographic distance
  Other contextual deviations
  These signals support the final risk assessment.

# 📊 Model Validation
The deployed SENTINEL champion model was evaluated using a held-out transaction dataset.

| Metric | Result |
|---|---:|
| Precision | 70.12% |
| Recall | 62.36% |
| F1 Score | 66.02% |
| Held-out transactions | 10,000 |
| False Positives | 72 |
| False Negatives | 102 |
| Operating Threshold | 45% |
### Understanding the Metrics
**Precision — 70.12%**
Approximately 70% of transactions flagged by the model were actually fraudulent in the held-out evaluation.
**Recall — 62.36%**
Approximately 62% of fraudulent transactions were detected in the held-out evaluation.
**F1 Score — 66.02%**
The F1 score provides a combined measure of precision and recall.
> These metrics represent the held-out evaluation used during model development. They should not be interpreted as guaranteed live production performance.

# 🧩 Build Challenges & Technical Obstacles
During development, several technical challenges were encountered.
## 1. Highly Imbalanced Fraud Data
Fraud transactions represent only a small portion of typical transaction datasets.
This creates a challenge because a model can achieve high overall accuracy while still performing poorly on fraudulent transactions.
### Solution
SENTINEL uses balanced class weighting during Random Forest training and evaluates precision, recall, and F1 score rather than relying only on accuracy.
---
## 2. Choosing the Operating Threshold
The default probability threshold is not always suitable for fraud detection.
A lower threshold can identify more suspicious transactions but may also increase false positives.
A higher threshold can reduce unnecessary intervention but may allow more fraudulent transactions to pass.
### Solution
SENTINEL performs threshold analysis and uses a validated operating point of:
```text
 45%
The threshold can be adjusted as the system evolves.
3. Combining Multiple Intelligence Sources
A machine-learning probability alone does not provide enough context for an analyst.
For example:
  AI Probability = 4%
does not explain what other transaction characteristics may be suspicious.
Solution
  SENTINEL combines:
  AI fraud probability
  Behavioral intelligence
  Relationship intelligence
  Anomaly/context signals
The result is a more informative risk assessment.
4. Explainable Risk Signals
A fraud system should not simply return:
FRAUD = TRUE
without explaining the supporting evidence.
Solution
  SENTINEL converts detected transaction patterns into human-readable risk signals.
  Examples include:
  Elevated transaction amount
  Unusual transaction time
  Elevated transaction distance
  Historical fraud association
  Historically linked transaction entities
This allows an analyst to understand the evidence contributing to the risk assessment.
5. Frontend and Backend Integration
The dashboard needs to communicate with the Python risk engine and display the result dynamically.
Solution
SENTINEL uses a FastAPI backend with JavaScript-based frontend communication.
  
  The workflow is:
  
  Web Dashboard
        ↓
  Transaction Request
        ↓
  FastAPI
        ↓
  SENTINEL Risk Engine
        ↓
  AI + Intelligence Layers
        ↓
  Risk Decision
        ↓
  JSON Response
        ↓
  Dashboard Update
6. Model and API Integration
The trained model is stored separately from the application logic.
The application must correctly load the model artifact and use the configured operating threshold.
Solution
  The deployed model is stored in:
  models/sentinel_fraud_model.pkl

The FastAPI application loads the trained model when the application starts.
A health endpoint is also provided to verify that the model and intelligence layer are operational.
7. Prototype-to-Production Gap
Building a working demonstration is different from operating a production fraud platform.
A production deployment would require additional capabilities such as:
  Authentication
  Authorization
  Secure data handling
  Monitoring
  Model drift detection
  Production databases
  Rate limiting
  Secure secret management
  Audit controls
  Infrastructure monitoring
Solution
SENTINEL is explicitly treated as a prototype / demonstration system, while the architecture is designed so that these production capabilities can be added later.

# ⚠️ Current Limitations
SENTINEL is currently a prototype / demonstration fraud-intelligence system.
The current implementation has some limitations:
- Model performance depends on the available training data.
- Validation metrics represent the held-out evaluation dataset.
- Behavioral and relationship intelligence can be expanded with larger historical datasets.
- The current system is not intended to directly process real customer payment data in production.
- Production deployment would require stronger security, monitoring, authentication, and data-governance controls.
- Risk thresholds should be recalibrated according to the requirements and fraud costs of a real payment environment.
